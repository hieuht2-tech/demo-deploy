FOOD MENU / TÀI LIỆU DẠY HỌC 01

Dạy tiếp từ project đang có

Food Menu: từ khung giao diện tới dữ liệu thật, rồi thêm tương tác bằng JavaScript.

Tài liệu này đi theo các file đã hoàn thiện trong thư mục demo-deploy. Giữ HTML/CSS và ảnh hiện có; không yêu cầu dựng lại website từ đầu. Mỗi chặng: mở file → chỉ ra vùng code → thử một thay đổi nhỏ → quan sát kết quả.

HTML / CSS→ Config→ Fetch JSON→ Chuẩn hóa→ DOM→ Sự kiện→ Validate→ Storage

Hai luồng cần đi hết

  1. Công thức: danh sách API → chi tiết theo type/ID → liên quan → lưu yêu thích → nhận xét.
  2. Thực đơn demo: JSON của quán → thêm giỏ → đổi số lượng → tài khoản → xác nhận → xem đơn.

Ba nguồn dữ liệu, ba vai trò

Cách chia buổi

Buổi 1: UI và request. Buổi 2: danh sách/chi tiết. Buổi 3: lưu dữ liệu/giỏ. Buổi 4: form, checkout và tự trình bày. Học sinh khá có thể gộp; không gõ tất cả file trong một lần.

Chạy bằng Live Server. Các trang nằm ở gốc, nên mọi đường dẫn assets/... và data/menu.json giữ tương đối, dùng được trên GitHub Pages.

1. Nhìn giao diện rồi mới nhìn JS

Mở: monan.html và assets/css/style.css. Cho học sinh phân biệt khu công thức API và thực đơn demo trước khi viết fetch.

Chỉ ra “nơi dữ liệu sẽ xuất hiện”

<input id="meal-search" type="search">
<button id="meal-search-btn" type="button">Tìm kiếm</button>
<p id="api-status" role="status" aria-live="polite"></p>
<div id="api-meal-list" class="row g-4" aria-busy="true"></div>

HTML chuẩn bị ô tìm, nút, thông báo và một vùng rỗng. JS sẽ đưa card vào vùng rỗng, không chép hàng chục card món ăn vào HTML.

Đọc CSS theo khối

  • .recipe-toolbar: hai cột trên máy tính, một cột trên điện thoại.
  • .food-card: ảnh, tên và nút có khoảng cách thống nhất.
  • .recipe-layout: ảnh và thông tin chi tiết; media query đổi thành một cột.
  • .surface, .cart-layout: khung form và tóm tắt đơn.

Bài thao tác nhỏ

  1. Đổi placeholder ô tìm; mở lại trang, chỉ ra nội dung thuộc HTML.
  2. Đổi khoảng cách của toolbar; chỉ ra thay đổi thuộc CSS.
  3. Đưa ô tìm về nguyên trạng, mở DevTools → Network → Fetch/XHR.
Học sinh cần nói được

UI là khung và trạng thái. Fetch lấy dữ liệu. Render đưa dữ liệu vào UI. Một thẻ div rỗng không có nghĩa là trang bị hỏng nếu JS đang tải dữ liệu.

Kết quả: xác định được bốn ID đầu vào/đầu ra, biết file CSS đang điều khiển vùng đó.

2. Lần theo request API

Mở: assets/js/config.js → assets/js/api.js.

Địa chỉ đặt ở một chỗ

const FOOD_CONFIG = {
  MEAL_URL: "https://www.themealdb.com/api/json/v1/1/",
  DRINK_URL: "https://www.thecocktaildb.com/api/json/v1/1/",
  DEFAULT_MEAL_SEARCH: "chicken"
};

/1/ là test key công khai dùng cho việc học, không cần học sinh đăng ký key riêng trong bài mẫu này.

Giảng đoạn rút gọn trước

const url = new URL("search.php", FOOD_CONFIG.MEAL_URL);
url.searchParams.set("s", "chicken");
const response = await fetch(url);
if (!response.ok) throw new Error("Không tải được dữ liệu");
const data = await response.json();
  1. fetch gửi request; await chờ Promise, không biến code thành đồng bộ toàn trang.
  2. HTTP 404/500 không tự làm fetch báo lỗi mạng. Cần response.ok.
  3. response.json() cũng trả Promise; cần await.
  4. Trong bản đầy đủ, AbortController hủy sau 20 giây và finally dọn timer.

Làm ngay trong Network

Tìm Chicken, chọn request search.php?s=chicken, mở Response. Cho học sinh chỉ ra meals, idMeal, strMeal. Đổi từ khóa rồi xem URL có thay đổi không.

Câu hỏi kiểm tra hiểu

Tại sao phải có cả response.ok và await response.json()? Nếu thấy “Failed to fetch” thì đã có đủ căn cứ nói API sai key chưa?

Nguồn: TheMealDB API, TheCocktailDB API.

3. Đọc JSON và chuẩn hóa

Mở: readArray(), normalize() và search() trong api.js.

EndpointDạng trả vềCần lấy
Meal search/filter{ meals: [...] }data.meals
Drink search/filter{ drinks: [...] }data.drinks
Không tìm thấymeals hoặc drinks bằng nullĐổi null thành []
if (data[property] === null) return [];
if (!Array.isArray(data[property])) {
  throw new Error("Dữ liệu nguồn không đúng cấu trúc");
}
return data[property];

Vì sao cần normalize?

Món ăn dùng idMeal/strMeal; đồ uống dùng idDrink/strDrink. UI chỉ nên đọc một kiểu object.

{
  id: "52795", kind: "meal", name: "Chicken Handi",
  image: "https://...", category: "Chicken", area: "India",
  instructions: "...",
  ingredients: [{ name: "Chicken", measure: "1.2 kg" }],
  sourceURL: "https://...", videoURL: "https://..."
}

Vòng lặp từ 1 đến 20 ghép strIngredientN với strMeasureN; bỏ nguyên liệu rỗng. Món chay gộp Vegetarian/Vegan, dùng Map bỏ ID trùng rồi lọc tên trên danh sách đã tải.

Thử ngay

Tìm một từ vô nghĩa: phải hiện không có kết quả, không xuất hiện lỗi “map is not a function”. Sau đó thử đồ uống và chỉ ra vì sao UI vẫn dùng lại được.

Kết quả: học sinh tự viết được object chuẩn hóa cho một món, không gọi map trực tiếp lên object response.

4. Một object thành một card

Mở: food-ui.js → catalog.js → monan.js.

const title = document.createElement("h3");
title.textContent = item.name;
const link = document.createElement("a");
link.href = "chitiet.html?type=" + item.kind + "&id=" + item.id;
link.textContent = "Xem công thức & đánh giá";

Card là các node DOM. Dữ liệu từ API đưa vào textContent, không ghép tên/mô tả trực tiếp vào innerHTML. Ảnh được gán src và có ảnh dự phòng.

Tách render khỏi fetch

// Ý chính của catalog.js; đối chiếu bản đầy đủ trong file.
const result = await FoodAPI.search(kind, input.value);
items = result;
const sorted = [...items];
sorted.sort((a, b) => a.name.localeCompare(b.name));
list.replaceChildren(...sorted.slice(0, visible).map(createRecipeCard));

items giữ mảng gốc. Bản sao được sắp xếp, slice chọn số card hiển thị. Xem thêm tăng 12; không gửi lại request vì dữ liệu đã có.

Sự kiện chỉ gắn một lần

Nút tìm/Enter gọi load; select gọi render; Xem thêm tăng số card rồi render. Không thêm event listener trong mỗi vòng render.

Request cũ không ghi đè request mới

const current = ++requestNumber;
const result = await FoodAPI.search(kind, input.value);
if (current !== requestNumber) return;
Bài cho học sinh

Tìm liên tiếp hai từ khóa; giải thích request nào được phép render. Đổi sort rồi thử Xem thêm. Chỉ ra trường hợp nào có request mới, trường hợp nào chỉ cập nhật DOM.

Wrapper: monan.js/douong.js/monchay.js chỉ truyền kind và các ID HTML vào cùng một hàm.

5. Từ card sang trang chi tiết

Mở: chitiet.html → detail.js → FoodAPI.lookup().

const params = new URLSearchParams(location.search);
const kind = params.get("type") || "meal";
const id = params.get("id");
const item = await FoodAPI.lookup(kind, id);

type chọn nguồn/loại dữ liệu; id chọn công thức. Hai loại có thể có ID khác hệ, nên link phải giữ cả hai. URL sai phải báo lỗi trước khi gọi nguồn.

Vì sao không dùng luôn object card?

filter.php chỉ trả tóm tắt tên/ảnh/ID. lookup.php mới có nguyên liệu và hướng dẫn. Lấy theo URL giúp refresh hoặc mở tab mới vẫn ra đúng món.

const view = document.querySelector("#recipe-detail-template")
  .content.cloneNode(true);
view.querySelector(".recipe-title").textContent = item.name;
view.querySelector(".recipe-directions").textContent = item.instructions;
detailRoot.replaceChildren(view);

Đọc template trong HTML

template không hiện sẵn. JS clone khung, điền dữ liệu rồi gắn vào DOM. Học sinh tìm các selector tương ứng giữa HTML và JS, không chỉ copy cả file.

Liên quan là một request riêng

FoodAPI.related(item) lọc cùng loại/nhóm, bỏ ID hiện tại và lấy tối đa bốn card. Lỗi phần liên quan chỉ báo ở vùng đó, không xóa chi tiết đã hiện.

Thử ngay

Mở link thiếu id, id sai và ID không tồn tại. Refresh một link đúng. Mở chi tiết đồ uống rồi chỉ ra request đang dùng TheCocktailDB chứ không phải TheMealDB.

Kết quả: một HTML dùng cho nhiều công thức, không tạo mỗi món một file.

6. Lưu công thức và đánh giá

Mở: favorites-store.js, favorites.js, reviews.js.

Bộ sưu tập chỉ lưu tham chiếu

[
  { kind: "meal", id: "52795" },
  { kind: "drink", id: "12560" }
]

Không cất toàn bộ object API. Khi mở yeuthich.html, đọc kind/ID rồi lookup để lấy thông tin. Giới hạn 30 công thức, tải nhóm ba để không gửi mọi request cùng lúc.

Đánh giá là dữ liệu local, không phải API bình luận

Các key cũ giữ nguyên: foodMenuMealReviews, foodMenuVegetarianReviews, foodMenuDrinkReviews. Mỗi key là object ID → mảng nhận xét.

const stars = Number(form.querySelector('[name="stars"]').value);
const comment = form.querySelector('[name="comment"]').value;
FoodReviews.add(kind, id, stars, comment);
renderRecipeReviews();
  • Sao nguyên từ 1 đến 5; comment sau trim từ 1 đến 500 ký tự.
  • Ghi storage thành công mới báo đã lưu, mới xóa nội dung ô nhập.
  • Nhận xét dùng textContent, có thể xóa dữ liệu nhận xét trên máy.
  • Bộ sưu tập và đánh giá hiện dùng chung trên trình duyệt, không cam kết đồng bộ tài khoản.
Thử ngay

Nhập toàn dấu cách rồi gửi; nhập nhận xét hợp lệ và refresh. Mở món khác để kiểm tra không lẫn ID. Thử nội dung chứa dấu < > và quan sát nó vẫn là chữ.

Kết quả: học sinh phân biệt được API cung cấp công thức và JavaScript lưu dữ liệu tương tác ở đâu.

7. Thực đơn JSON và giỏ theo ID

Mở: data/menu.json → menu-api.js → menu.js → cart-store.js.

// menu.json: giá do quán demo quy định
{ "id": "menu-1", "kind": "meal", "name": "...",
  "price": 55000, "image": "assets/images/...", "description": "..." }

// localStorage: chỉ lưu tham chiếu + số lượng
[{ "id": "menu-1", "quantity": 2 }]

MenuAPI.all() fetch file JSON local. Trên GitHub Pages, file vẫn được phục vụ qua HTTP, không cần server Node. Không mở bằng file:// vì fetch file local có thể bị trình duyệt chặn.

Đọc CartStore.add()

  1. Kiểm tra ID và số lượng nguyên dương.
  2. Tìm món cùng ID trong giỏ bằng find.
  3. Có rồi thì cộng quantity, chưa có thì push.
  4. Tổng một món không vượt 99.
  5. Ghi storage, phát cart-updated để badge cập nhật.

Render giỏ lấy lại nguồn giá

const menu = await MenuAPI.all();
const lines = CartStore.read().map(item => ({
  ...item, product: menu.find(product => product.id === item.id)
}));

Giá không lấy từ chữ trên HTML hoặc giá cũ trong storage. ID không còn trong menu phải báo và yêu cầu xóa trước khi đặt đơn. Số lượng lỗi không được âm thầm làm tròn.

Quy tắc bài mẫu

Phí giao 15.000đ khi tạm tính dưới 200.000đ; từ 200.000đ miễn phí. Giỏ trống không tính phí. Cả giỏ và checkout dùng CartStore.totals(), tránh hai nơi tính khác nhau.

Kết quả: thêm hai lần cùng món chỉ có một dòng, refresh vẫn giữ giỏ và đúng giá nguồn.

8. Form, tài khoản và đơn demo

Mở: storage.js → auth.js → checkout.js → orders.js.

Hai lớp kiểm tra form

  • HTML: required, type=email, minlength, maxlength, min/max/step.
  • JS: trim, tên toàn khoảng trắng, email trùng, số nguyên, xác nhận mật khẩu, điều kiện giỏ.

reportValidity() kiểm tra thuộc tính HTML trước; validate JS kiểm tra quy tắc của chức năng. Báo lỗi ở vùng aria-live, không xóa nội dung khi chưa lưu được.

Tài khoản

Đăng ký chuẩn hóa email/tên đăng nhập, chặn trùng; đăng nhập so sánh đúng mật khẩu, không trim mật khẩu. Phiên currentUser chỉ chứa tên/username/email. users vẫn là dữ liệu demo lưu mật khẩu dạng rõ: chỉ dùng mật khẩu giả.

Xác nhận đơn đúng thứ tự

Kiểm tra đăng nhập→ Validate form→ Đọc lại giỏ/menu→ Tính lại tiền→ Lưu đơn→ Xóa giỏ→ Lịch sử đơn

Đơn lưu snapshot tên/giá/số lượng tại thời điểm đặt. Danh sách đơn lọc theo email của phiên trên trình duyệt. Có chặn submit liên tiếp; form sai không được xóa giỏ.

Liên hệ

Form kiểm tra họ tên, email, điện thoại nếu nhập và độ dài nội dung; lưu foodMenuMessages rồi báo rõ chưa gửi email/server. Không hiển thị “đã liên hệ cửa hàng” khi chỉ lưu local.

Giới hạn sản phẩm mẫu

Hoàn thiện luồng frontend không có nghĩa đã có thanh toán, giao hàng hoặc auth backend. GitHub Pages chỉ phục vụ file tĩnh; dữ liệu localStorage khác nhau theo tên miền, cổng và trình duyệt.

Kết quả: một đơn demo hợp lệ hiện ở donhang.html, giỏ hết; đơn không hợp lệ giữ giỏ.

Kịch bản demo trong 15 phút

  1. Chạy trang chủ, mở Network để thấy API và file JSON.
  2. Tìm Chicken; đổi A–Z, bấm Xem thêm, hỏi thao tác nào có request mới.
  3. Mở chi tiết, chỉ URL, nguyên liệu, liên quan; lưu và nhận xét.
  4. Chọn món ở thực đơn demo, tăng số lượng trong giỏ.
  5. Thử nhập 1.5: giải thích vì sao không chấp nhận.
  6. Đăng nhập demo; thử form địa chỉ sai rồi sửa đúng và lưu đơn.
  7. Mở lịch sử; nói rõ dữ liệu chưa đi đến server.

Bài tập mở rộng sau khi hiểu luồng

  • Thêm nút xóa từ khóa và phục hồi thứ tự mặc định.
  • Hiện tổng nguyên liệu hoặc đánh dấu nguyên liệu đã chuẩn bị.
  • Thiết kế bộ sưu tập theo từng tài khoản, có cách chuyển dữ liệu guest.
  • Thêm trang xem các lời nhắn demo của chính người đang dùng máy.
Đầu ra cần đánh giá

Học sinh tự giải thích một request, một lần render và một lần ghi storage; tự chỉ ra file khi chức năng lỗi. Không chấm chỉ bằng việc giao diện giống bài mẫu.

Thứ tự script dùng chung: storage → config → menu-api → cart-store → app. Sau đó nạp các file riêng của trang. Bản này dùng script thường/defer, không tự thêm type=module.
